# Downscaled CMIP6 Climate Indicators

Computes climate indicators (`su`, `dw`, `ftc` — see "What it does" below)
from WRF-downscaled, bias-adjusted CMIP6 data and the WRF-downscaled ERA5
reference, for 13 CMIP6 models plus a multi-model ensemble mean. Each
indicator is a *yearly* count of qualifying days; this pipeline pools
those per-year counts across a configurable historical/future era and
reduces them to a temporal min/mean/max, the same era/aggregation
framework `../climatologies/` uses for raw variables. Produces a single
master output (identical content in Zarr and NetCDF) with dimensions
`model, scenario, era, period, aggregation, y, x`.

## Quick start

```sh
conda activate cmip6-utils
cd cmip6-utils/indicators_ds
bash slurm/run_pipeline.sh --config config_12km.yaml
```

That rebuilds the job list from whatever's currently on disk, regenerates
the SLURM scripts from `config_12km.yaml`, and submits two jobs to the
`analysis` partition: a fragment-computation array job, then a combine job
that runs automatically once every fragment task succeeds. Check progress
with `squeue --me`. For reference, the first full run (153 jobs, array
concurrency 12) took under 7 minutes start to finish. When it's done, the
result is at:

```
${paths.output_root}/output/cmip6_wrf_indicators.zarr
${paths.output_root}/output/cmip6_wrf_indicators.nc
```

Then run the QC and clean up the intermediate fragments:

```sh
sbatch slurm/submit_qc.sbatch
# check ${paths.output_root}/qc/{nan_checks,calc_checks}.log and
# ${paths.output_root}/qc/delta_maps/ before proceeding
python cleanup_intermediate.py --config config_12km.yaml --yes
```

(`submit_qc.sbatch` already points at `config_12km.yaml` — it was
regenerated by `slurm/generate_sbatch.py` as part of the
`run_pipeline.sh --config config_12km.yaml` call above.)

## What it does

Input data is the same WRF-downscaled, bias-adjusted `tasmax`/`tasmin`
used by `../climatologies/` (see that pipeline's README for the input
directory layout) — `su` needs `tasmax` only, `dw` needs `tasmin` only,
`ftc` needs both.

The pipeline reduces daily `tasmax`/`tasmin` down to 3 output variables,
each shaped `(model, scenario, era, period, aggregation, y, x)`:

| Variable | Meaning |
|---|---|
| `su` | yearly count of days with `tasmax > 25 degC` ("summer days") |
| `dw` | yearly count of days with `tasmin < -30 degC` ("deep winter days") |
| `ftc` | yearly count of days with `tasmin <= 0 degC AND tasmax > 0 degC` on the same day ("freeze-thaw cycles") |

- **Model**: the 13 CMIP6 models, plus `CMIP6-Ensemble` (a multi-model
  mean) and `WRF-ERA5` (the reference; only populated under
  `Scenario=historical`).
- **Scenario**: `historical`, `ssp126`, `ssp245`, `ssp370`, `ssp585`.
- **Era**: configurable date ranges (e.g. `1981-2010`, `2040-2069`) —
  identical list to `../climatologies/`'s.
- **Period**: this first pass only defines `Annual` (a single period
  covering all 12 months) — see "Design decisions" below for why this is
  a config-only choice, not a structural limitation.
- **Aggregation**: `temporal_min`, `temporal_mean`, `temporal_max` — but
  note what's being aggregated here is different from climatologies (see
  "Design decisions").

Not every model has `tasmax`/`tasmin` data (`CESM2` has none at all, so
it's NaN throughout for all three indicators); see "Variable, Model, and
Scenario Support" below. Missing combinations are simply `NaN` — this is
expected, not a bug.

## How it works

Four stages, each its own script:

1. **`build_job_list.py`** scans the input directories on disk (it never
   hardcodes which models/scenarios exist) and writes
   `intermediate/job_list.json` — one entry per (indicator, model,
   scenario) combination that has the source variable(s) that indicator
   `requires`. For `ftc` this is the intersection of `tasmax` and
   `tasmin` coverage (the same pattern climatologies uses for its
   `tmean` derived variable).
2. **`compute_fragment.py`** — run once per `job_list.json` entry (as a
   SLURM array task). Loads the *entire* daily time series for that
   indicator's required source variable(s), then computes every era x
   period x aggregation value via `count_aggregate`: for each period,
   count qualifying days (the indicator's day-level criterion — see
   `CRITERIA` in this file) per calendar year, excluding incomplete
   season-years at the series' edges; then for each era, take
   `temporal_min`/`temporal_mean`/`temporal_max` across those per-year
   counts. This generalizes climatologies' `pr_tot_aggregate` (sum-per-year,
   then min/mean/max-across-years) from summing values to counting days.
   Writes a small "fragment" zarr
   (`intermediate/fragments/{indicator}__{model}__{scenario}.zarr`).
3. **`combine.py`** assembles every fragment into the full master arrays,
   fills in `NaN` for any (model, scenario) combination with no fragment
   at all, computes the `CMIP6-Ensemble` mean, and attaches all
   attributes (via `metadata.py`).
4. **`write_outputs.py`** writes the combined dataset to both Zarr and
   NetCDF.

`slurm/run_pipeline.sh` runs stage 1, regenerates the SLURM scripts for
stages 2-4 from the given `--config` (via `slurm/generate_sbatch.py`), and
submits the stage-2 array job followed by a stage-3+4 job chained with
`--dependency=afterok`.

## Running against multiple input datasets

Every script takes an explicit `--config <file>` (default
`config_12km.yaml` if omitted). So far there's only `config_12km.yaml` —
a 4km config is future work (see `~/INDICATORS_PLAN.md`) — but the
pattern is the same one `../climatologies/` uses for its `config_12km.yaml`
/ `config_4km.yaml`: one config YAML per input dataset rather than a
single `config.yaml`, since the source data paths, grid reference, and
`paths.output_root` all differ between resolutions. When adding a new
one:

- Copy `config_12km.yaml` and update its `paths.output_root` (so runs
  don't write into each other's output) and the `source_families.*`
  paths (`adjusted_glob`, `era5_zarr`) and `grid_reference.zarr_path`.
- Always pass the same `--config` to every script for a given run —
  `build_job_list.py`, `compute_fragment.py`, `combine.py`, `qc.py`,
  `cleanup_intermediate.py`, and `slurm/generate_sbatch.py` (and therefore
  `slurm/run_pipeline.sh`) all accept it.
- `slurm/generate_sbatch.py` writes `submit_fragments.sbatch`,
  `submit_combine.sbatch`, and `submit_qc.sbatch` with the `--config` path
  it was given baked in. Those three files are shared, generated
  artifacts — regenerating them for one dataset overwrites the version
  for any other, so don't run two datasets' pipelines concurrently.

## Editing the config

**`config_12km.yaml` is the place to change most parameters or any piece
of descriptive text that ends up in the output** — eras, periods, models,
ensemble membership, input paths, SLURM resources, QC plausibility
bounds, and all `metadata:` text. One exception: **the indicator
thresholds/operators themselves (`25 degC`, `-30 degC`, `0 degC`, and
which comparison operator each uses) live in `compute_fragment.py`'s
`CRITERIA` dict, not in the YAML.** That's a deliberate deviation from
the "every editable value is in the config" convention this repo
otherwise follows — see "Design decisions" below for why, and flag it if
you'd rather have these move into the config too.

- **Eras** — add, remove, or change the `eras:` list (each has a `name`,
  `start_year`, `end_year`).
- **Periods** — the `periods:` list (each has a `name` and `months:` in
  chronological order). Currently just `Annual`; adding a sub-annual
  period (e.g. `JJA`) is a config-only change — no code changes needed.
- **Models / ensemble membership** — `models:` is the full model list;
  `ensemble.members:` is the (possibly smaller) subset averaged into
  `CMIP6-Ensemble`.
- **Input paths** — `source_families.tasmax`/`tasmin`'s `adjusted_glob` /
  `era5_zarr`.
- **Indicator definitions** — `indicators:` block: `requires` (which
  source variables), `units`, `long_name`, `description`, and
  `plausible_min`/`plausible_max` (QC range bounds — see "QC" below). Not
  the threshold values themselves, see above.
- **SLURM resources** — `slurm:` (partition, mem, cpus, time, and the
  array concurrency throttle for the fragment stage).
- **Any text in the output's attributes** — the `metadata:` section
  (dataset title/institution/summary, the per-dimension description
  templates). See "Why dataclasses" below for why this is safe to edit
  freely.

## Design decisions

- **`count_aggregate`'s two-stage method.** Every indicator here is a
  day-count, so there's no sensible "daily value" to take a direct
  min/mean/max of the way climatologies does for most of its variables —
  a single day's "value" is just a 0/1 threshold flag. So every indicator
  uses a two-stage method: count qualifying days per calendar year first,
  then `temporal_min`/`temporal_mean`/`temporal_max` across those
  per-year counts within an era. This generalizes climatologies'
  `pr_tot_aggregate` (sum-per-year, then min/mean/max-across-years) from
  summing values to counting days.
- **Annual-only period, for now.** `su`/`dw`/`ftc` are conventionally
  whole-year counts. Rather than special-case "no period axis," the
  `period` dimension just has one entry (`Annual`, months 1-12) — the
  exact same `periods.py` logic climatologies uses for e.g. `JJA` handles
  this as an ordinary non-wrapping period. Adding sub-annual breakdowns
  later only requires editing the config's `periods:` list.
- **Thresholds are plain comparisons, not `xclim` calls.** `xclim`'s
  indicator functions (e.g. a "days above threshold" counter) resample on
  a fixed frequency (e.g. yearly-start) — they don't know about this
  pipeline's custom era/period/label-year buckets. Rather than fight that
  API, each indicator's day-level criterion is a plain boolean comparison
  in `compute_fragment.py`'s `CRITERIA`, applied within the same
  per-period/per-year masking `periods.py` already provides. This
  pipeline has no runtime dependency on `xclim`.
- **`CMIP6-Ensemble` and missing data.** Same as climatologies: a
  `nanmean` across whichever configured member models actually have
  non-NaN data for a given slice — only `NaN` if *zero* members have
  data.

## QC

`qc.py` validates the *pipeline*, not the source data — the source data
has already been through its own QC process (see
`../climatologies/qc.py`, which checks the same `tasmax`/`tasmin` inputs
this pipeline reads). Every check compares quantities this pipeline
itself computed against a relationship that must hold if the computation
is correct.

Run manually after a pipeline run:

```sh
sbatch slurm/submit_qc.sbatch
```

Writes to `${paths.output_root}/qc/`:
- `nan_checks.log`: a coverage-gap cross-check against
  `intermediate/fragments/` (if a fragment exists, the output must have
  *some* non-NaN data, and vice versa).
- `calc_checks.log`: `min<=mean<=max`; `temporal_min`/`temporal_max` are
  exact integers for every real model (they're literal per-year counts,
  never averaged — `CMIP6-Ensemble` is excluded from this one check since
  it's a nanmean *across models* of each model's own integer min/max,
  which is itself generally fractional, not a bug); non-negativity;
  values fall within each indicator's configured
  `plausible_min`/`plausible_max`; ensemble re-derivation. Ends with a
  one-line `ALL CHECKS PASSED` / `N TOTAL VIOLATIONS` summary.
- `delta_maps/<var>/<var>__<period>.png`: one PNG per indicator x every
  configured period (just `Annual` for now), each an 8-panel scenario x
  era grid of
  `CMIP6-Ensemble[scenario,era] projection - WRF-ERA5[historical baseline]`.

Once you've reviewed the QC output, run `python cleanup_intermediate.py
--yes` to delete `intermediate/fragments/` (defaults to a dry run without
`--yes`); do this *after* QC, not before, since the coverage-gap
cross-check reads fragment filenames.

All of the QC parameters (the baseline era, which scenarios/eras get
delta maps, the per-indicator plausibility bounds) live under the
config's `qc:` section and each indicator's `plausible_min`/`plausible_max`.

## Why dataclasses in `config.py`

`config.py` defines a handful of `@dataclass`-decorated classes (`Era`,
`Period`, `SourceFamily`, `IndicatorDef`, `Config`) that `load_config()`
parses a config YAML into. They hold **zero hardcoded values** — every
field's value still comes from the config YAML; this is just a loader,
not a second configuration file.

The benefit: the same `Config` object gets passed into every script
(`build_job_list.py`, `compute_fragment.py`, `combine.py`, `metadata.py`,
`qc.py`, `slurm/generate_sbatch.py`). With a typed object, a typo like
`config.eras[0].start_yera` is caught by your editor before you even run
anything; with a plain dict, the equivalent
`config["eras"][0]["start_yera"]` only fails at runtime, possibly deep
inside a job that takes a while to get there. `frozen=True` makes the
loaded config read-only, so nothing downstream can accidentally mutate
shared configuration mid-run.

## File reference

| File | Role |
|---|---|
| `config_12km.yaml` | every tunable parameter and every piece of output-facing text — pass via `--config` (see "Running against multiple input datasets" above) |
| `config.py` | loads a config YAML (default `config_12km.yaml`) into typed objects (no values of its own) |
| `periods.py` | period-membership and season-year ("label year") logic |
| `units.py` | K -> degC conversion for `tasmax`/`tasmin`, driven by the config's `units:` section |
| `source_catalog.py` | glob/regex helpers for discovering what's on disk |
| `build_job_list.py` | stage 1 — writes `intermediate/job_list.json` |
| `compute_fragment.py` | stage 2 — one job -> one fragment zarr; `count_aggregate` + per-indicator `CRITERIA` |
| `metadata.py` | builds output attrs by filling config YAML templates (no hardcoded text) |
| `combine.py` | stage 3 — fragments -> master Dataset, ensemble, NaN-fill |
| `write_outputs.py` | stage 4 — master Dataset -> Zarr + NetCDF |
| `qc.py` | validates the pipeline's own calculations + renders delta maps (run manually, see "QC" above) |
| `cleanup_intermediate.py` | deletes `intermediate/fragments/` (run manually, after `qc.py`, see "QC" above) |
| `slurm/generate_sbatch.py` | writes `slurm/submit_fragments.sbatch` / `submit_combine.sbatch` / `submit_qc.sbatch` from the given config's `slurm:` section |
| `slurm/run_pipeline.sh` | runs stage 1, regenerates sbatch scripts, submits the SLURM jobs (fragments + combine only; `qc.py`/`cleanup_intermediate.py` are run separately) |
